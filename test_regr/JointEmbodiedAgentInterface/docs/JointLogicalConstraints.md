# Joint logical knowledge and constraint inventory

Checked on **2026-10-22**. The joint interface shares a backbone and three semantic parent concepts. Its authoritative logical knowledge is declared in the EAI and VLABench domain graphs, not duplicated in a separate joint rule set. This document exposes graph ownership, observation binding, activation and provenance. Full rule-family examples are in [EAI logical constraints](../../EmbodiedAgentInterface/docs/EAILogicalConstraints.md) and [VLABench logical constraints](../../VLABenchAgentInterface/docs/VLABenchLogicaConstraints.md).

## Concepts and ownership

The joint graph declares episode, entity and operation parents. Both domains specialize these through is_a relationships. There are **zero additional joint behavioral constraints**. A shared parent does not assert that right_grasp and pick are equivalent: their argument/state contracts differ. No cross-domain equivalence table has been supplied, so no such knowledge is assumed or hidden in procedural code.

Names outside quotes identify concepts/operators; names inside quotes bind logical variables. The following is the shared ontology structure, not additional logical constraints:

```python
with Graph("joint_embodied_world") as root:
    episode = Concept(name="embodied_episode")
    entity = Concept(name="embodied_entity")
    operation = Concept(name="embodied_operation")
    parents = {"episode": episode, "entity": entity, "operation": operation}
    eai = build_eai_world_graph(semantic_parents=parents,
                              include_default_constraints=True)
    vlabench = build_vlabench_world_graph(semantic_parents=parents,
                                        include_default_constraints=True)
```

The implementation is <a href="../world_graph.py#L35"><code>world_graph.py:35</code></a>. Compilation, activation locks, policy binding and budgets now live in <a href="../utils/generation_runtime.py#L37"><code>generation_runtime.py:37</code></a>. Former imports from world_graph remain available through compatibility exports.

## Counts and declaration sources

Count one complete formula as one logical constraint: ifL(A, andL(B, C)) counts as one. Nested operators, concepts, relation declarations, activations, requirement observations and DFA states do not add constraints. A grounded evaluation applies one declaration to a particular action, token pair or requirement.

## Knowledge provenance and checkpoint behavior

Schema/vocabulary checksums keep their established compatibility meaning. A separate runtime.knowledge_manifest exposes the actual ontology parents, complete formulas, variable paths/relations, count limits, priorities, context bindings, declaration counts and activation flags. It records compiled predicate-program fingerprints plus auxiliary/parametric declaration-source fingerprints. Stable component labels replace build-specific graph names and role IDs; prose and formatting do not alter source fingerprints. Source hashes intentionally also capture the binding/grounding implementations that supply domain observations.

Definition and activation fingerprints are separate. The manifest records VLABench knowledge tier as well as active formulas, so learned/task fact-source changes remain visible. <a href="../utils/knowledge_manifest.py#L43"><code>knowledge_manifest.py:43</code></a> constructs the inventory; <a href="../utils/knowledge_manifest.py#L220"><code>knowledge_manifest.py:220</code></a> validates it before model/optimizer/RNG restoration.
